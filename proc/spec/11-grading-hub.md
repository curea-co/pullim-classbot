## 1. AI 명령지침 (이 spec 한정)

- 이 문서를 단일 진실원으로 본다. 권위 문서와 충돌하면 권위 문서를 따르고 본 spec을 갱신한다.
- **개발 시작 전 반드시 검토할 것**:
  1. `gradingQueue` mock의 모든 필드를 화면에서 소비하는지
  2. "AI 초안 = 제안, 교사 = 판결" 디자인 원칙 (핸드오프 § 2.5) 위반하지 않는지
  3. 객관식·서술형·단답형 3타입 모두 동일 큐에서 처리되는지
  4. **채점 대기가 없는 학생도 목록에 남는지** — 채점 허브는 「채점할 게 있는 학생」이 아니라
     **등록된 학생 전체**를 본다. 큐만 보이면 오늘 제출하지 않은 학생이 화면에서 사라진다
  5. 학생 상세 **화면**을 새로 만들지 않았는지 — 대화 기록·과정 평가·이탈 이력은 `/teacher/students/[id]` 가
     이미 한다. **그 화면에 더하는 신규 UI 는 패널 두 개뿐이다** — 「막힌 지점」 · 「이 학생의 채점」 (§ 3.3.3)
- 추출본 정책: 다른 도메인(플래너/Q/라이브러리) 의존 금지. 채점 허브는 클래스봇 단일 도메인 내부에서 자급한다.
- **금지**: AI 점수를 학생/학부모에게 직접 노출. 반드시 교사 승인 후에만 학생·학부모 가시.

## 2. 제품 정의 (Problem · Goal · Persona)

### 2.1 Problem Statement
공교육 교사·학원 강사의 서술형 채점은 1인당 2주 → 평균 채점 소요시간이 학생 피드백 사이클을 끊는다. 객관식은 자동화됐지만 서술형·단답형은 여전히 수작업이고, 채점 일관성도 교사 컨디션에 좌우된다.

### 2.2 Product Goal
- **G1**: 서술형 채점 소요시간 **80% 단축** (KPI § 10.2)
- **G2**: 교사는 "초안 검수자"로 역할 전환 — 점수 작성 → 점수 확인·수정
- **G3**: 교사 수정 데이터가 루브릭 재학습으로 환류 (선순환 폐쇄)

### 2.3 Persona별 영향

| 페르소나 | 역할 | 이 기능에서 무엇이 달라지나 |
|---|---|---|
| **P1 교사** (주) | 채점자 | 큐에 쌓인 AI 초안을 검수·승인. 변경률 20% 초과 시 루브릭 재학습 제안 수락 |
| **P2 학생** | 응시자 | 제출 후 평균 24시간 → 6시간 내 피드백 수신 |
| **P3 학부모** | 열람자 | 최종 점수만 노출 (AI 초안은 안 보임) |
| **P4 학원 관리자** | 감독자 | 강사별 검수 평균 소요 / 변경률 KPI 열람 |

## 3. 핵심 기능 정의 (FSD)

### 3.1 MoSCoW

#### Must (MVP)
- [M0] **등록 학생 전체 목록** — 기본 화면. 채점 대기가 0건인 학생도 빠지지 않는다
- [M0-1] 학생 한 줄 요약을 **배지**로 — 도달 상태 · 최근 접속 · 채점 대기 건수
- [M0-2] 학생을 누르면 `/teacher/students/[id]` 상세로 — 어떤 봇과 무슨 대화를 했고 어디서 막혔는지
- [M1] 채점 큐 화면 — 상태별 필터 (대기/검토중/완료)
- [M2] 채점 상세 화면 — AI 초안 + 루브릭 항목별 점수 표시
- [M3] 교사 인라인 편집 — 점수·코멘트·루브릭 항목 수정
- [M4] 승인 / 오버라이드 액션 — 학부모 가시화 트리거
- [M5] 변경률 자동 계산 + 20% 임계 알림

#### Should (v1)
- [S1] 상위 10% / 하위 10% 자동 분석 패널 (T3)
- [S2] 일괄 작업 — 다중 선택 → 일괄 승인
- [S3] 루브릭 재학습 제안 모달 — 교사 승인 시 다음 과제부터 적용
- [S4] 학생별 채점 이력 사이드 패널
- [S5] **봇 · 과제 필터 칩** — 다중 봇·다중 학급 운영의 거르개. 지금은 mock 에 학급이 한 벌뿐이라
  칩을 둘 값이 없다. 화면 구조는 이미 그 확장을 막지 않는다 (아래 참조)

#### Could (v2)
- [C1] 손글씨 답안 OCR + 채점 (수학 풀이 과정)
- [C2] AI 음성 코멘트 자동 생성 (교사 목소리 TTS)
- [C3] 표절·AI 작성 의심 플래그

#### Won't (현 단계 제외)
- 자동 점수 학부모 직접 발송 (반드시 교사 승인 게이트 통과)
- AI가 만점 처리 (모든 항목 최소 1초간 교사 시선 보장 — 안티 패턴 방지)

### 3.2 Sitemap 변경

```
/teacher
├─ /teacher/grading                 ← 채점 허브 입구
│  ├─ ?view=students                ← **기본** · 등록 학생 전체 (배지 요약)
│  ├─ ?view=queue                   ← 채점 대기 큐 (필터·정렬·일괄 액션)
│  ├─ /teacher/grading/[id]         ← 채점 상세 (AI 초안 검수)
│  └─ ?status=…&type=…              ← URL 상태 (큐 화면 한정)
│
└─ /teacher/students/[id]           ← 학생 상세 — 채점 허브 목록이 여기로 보낸다 (신규 아님)
```

**들어오는 곳마다 열리는 탭이 다르다.** 기본이 학생 전체로 바뀌어도 「채점하러 왔다」는 동선은
큐로 곧장 들어가야 한다 — 그러지 않으면 가장 빈번한 채점 흐름(Flow G1 · 핸드오프 Flow C)이 학생 목록으로 샌다.

| 들어오는 곳 | 열리는 화면 | 왜 |
|---|---|---|
| 교사 홈 「나를 기다리는 일 · 서술형 채점 대기 N건」 | `?view=queue` | 그 카드는 **검수할 것**만 가리킨다 |
| 채점 상세의 「채점 대기 큐로」 | `?view=queue` | 검수하던 자리로 돌아간다 |
| 사이드바 「채점 허브」 | 기본 (학생 전체) | 목적 없이 들어오는 자리 — 학급 전체를 먼저 본다 |
| 학생 상세 「이 학생의 채점」 | `/teacher/grading/[id]` 로 직행 | 이미 학생을 고른 뒤다 |

교사 홈·채점 상세처럼 **큐로 들어와야 하는 링크에는 `?view=queue` 를 반드시 붙인다.**
붙이지 않은 링크는 학생 전체로 열린다.

**학생 명단은 화면마다 따로 세지 않고 한 곳에서 읽는다.** 같은 명단을 보는 화면이 여럿이어도
판정(도달 배지·최근 접속)은 한 곳에서만 한다.

지금 그 한 곳은 `monitoredRoster` 이고, 이것은 **현재 학생 목록이 읽는 단일 UI 원천**일 뿐이다.
**등록 명단(enrollment)의 진실원이 아니다** — 그 파일은 스스로를 「학급 한 반(중1-3반 과학) 관제 스냅샷」이라
적어 두었고 담은 필드도 관제 지표뿐이다. enrollment 는 BE 가 내려줄 별도 원천이고,
그때 이 화면은 원천만 갈아 끼운다 — 학생 목록이 명단을 **인자로 받기** 때문이다
(`buildGradingRoster(items, roster)`). 관제 mock 에 enrollment 역할을 얹지 않는다.

같은 이유로 학생 상세가 보여주는 학급·봇·단원(중1-3반 과학 · 과학봇 · 물질의 상태 변화)도
**그 mock 이 지금 담고 있는 임시 컨텍스트**다. 채점 시드를 그 컨텍스트로 정렬한 것(§ 7.1)은
두 화면이 어긋나지 않게 맞춘 것이지, 그 과목이 제품의 정답이라는 뜻이 아니다.

**한 학급으로 좁히는 것이 아니다.** 지금 mock 에 학급이 한 벌뿐이라 한 벌이 보이는 것이고,
학생 목록은 **명단을 인자로 받는다**(`buildGradingRoster(items, roster)`). 명단이 여러 학급으로 늘면
그대로 늘어나고, 그때 봇·과제 칩([S5])이 위 거르개 줄에 붙는다. `/teacher/*` 운영 라우트가
다중 봇·다중 학급 entry 라는 03 의 정의(§ 2.2)는 그대로 유지된다.

| 화면 | 무엇을 위해 | 링크되는가 |
|---|---|---|
| 학급 관제소 `/teacher/monitor` | 학급 진단 — 다시 가르칠 개념 + 20줄 | ✅ 사이드바 |
| **채점 허브 `?view=students`** | **검수 관점** — 채점 대기 배지가 붙은 같은 명단 | ✅ 사이드바 (채점 허브) |
| `/teacher/students` | `/teacher/students/[id]` 의 부모 경로가 빈 화면이 되지 않게 둔 얇은 화면 | ❌ 어디서도 링크하지 않는다 |

`/teacher/students` 는 목록 **진입점이 아니다.** 목록으로 들어가는 길은 관제소와 채점 허브 탭 둘뿐이고,
`/teacher/students/[id]` 만 두 화면이 함께 쓰는 **상세** 라우트다.

두 화면을 한 라우트 안에서 **탭으로** 가른다. 거르개를 두 벌 겹쳐 두지 않기 위해서다 —
학생 목록의 거르개(도달·접속·채점 대기)와 큐의 거르개(상태·타입)는 서로 다른 것을 거른다.
같은 화면에 함께 두면 지금 무엇이 걸려 있는지 읽을 수 없다.

학생 영역에 채점 진입 없음 — 학생은 "결과 보기" CTA로 [학생 과제 풀이 결과 페이지](12-student-assignment-solve.md § 3.2)에서 최종 점수만 확인.

### 3.3 Screen Spec

#### 3.3.0 학생 전체 (`/teacher/grading?view=students`) — **기본 화면**

| 구성 | 설명 |
|---|---|
| **상단 KPI 바** | 채점 큐와 같은 4칸 (대기 · 검토중 · 오늘 승인 · 평균 변경률) |
| 탭 | `학생 전체`(기본) · `채점 대기 큐` |
| 거르개 | 전체 · 채점 대기 있음 · 미도달 · 오늘 안 들어옴 |
| 정렬 | 채점 대기 많은 순(기본) · 이름순 · 활동 오래된 순 |
| **학생 행** | 이름·학년 / 도달 배지 / 최근 접속 배지 / 채점 대기 배지 / 막힌 개념(첫 한 가지) / 대기가 있으면 그 한 건의 AI 초안 점수 |
| 행을 누르면 | `/teacher/students/[id]` — 대화 기록 · 막힌 지점 · 과정 평가 |
| 빈 상태 | 거르개에 걸린 학생이 없을 때만. **등록 학생이 0명이 아닌 한 목록은 비지 않는다** |
| 목록 아래 안내 | 「대기 0건이어도 학생은 목록에 남는다」는 이유 한 줄. 채점 항목은 모두 어느 학생 줄엔가 붙으므로 별도 각주는 두지 않는다 (§ 7.1) |

배지가 말하는 것과 그 출처:

| 배지 | 무엇을 말하나 | 출처 |
|---|---|---|
| 도달 (도달·미달·미도달) | 성취기준에 닿았는지, 요구한 사고 수준까지 갔는지 | `reachBadge()` — 관제소·교사 홈과 같은 판정 |
| 최근 접속 | 마지막 활동이 언제였는지, 오늘 들어왔는지 | `lastSeenText()` · `isOfflineToday()` |
| 채점 대기 | 이 학생 앞으로 검수할 채점이 몇 건인지 (0건이면 「대기 없음」) | 교사 확정(store) 반영 후 `status === 'queue'` 인 건수 |

**없는 지표를 새로 만들지 않는다.** 세 배지 모두 이미 다른 화면이 쓰던 판정을 그대로 읽는다 —
같은 학생이 화면마다 다르게 읽히면 안 된다.

#### 3.3.1 채점 대기 큐 (`/teacher/grading?view=queue`)
| 구성 | 설명 |
|---|---|
| **상단 KPI 바** | 대기 N건 · 검토중 N건 · 오늘 승인 N건 · 평균 변경률 N% |
| 필터 칩 | 상태 `status=all\|queue\|reviewing\|approved\|overridden` (**기본 `queue`**), 타입 `type=all\|essay\|short\|numeric` (기본 `all`) |
| 상태 칩 이름 | `전체` · `대기` · `검토중` · `완료`(=`approved`) · `오버라이드`(=`overridden`) — **`all` 칩은 반드시 둔다.** 기본이 `queue` 라 확정된 항목이 기본 화면에서 안 보이는데, 어느 상태의 항목이든 되짚어 볼 길은 있어야 한다 |
| 봇 · 과제 칩 | **아직 없다.** 지우기로 한 것이 아니라 mock 에 봇·과제가 여러 벌 들어오면 붙일 자리다 — [S5] 참조 |
| 정렬 | 제출 시간 / AI 신뢰도 / 위기 신호 우선 |
| **채점 행** | 학생명·과제·타입·AI 점수·신뢰도·상태·"검수" CTA |
| 위기 신호 인디케이터 | `aiConfidence < 70` 또는 응답 빈약·감정 키워드 |
| 일괄 액션 바 | 다중 선택 시 노출 — "선택 N건 승인" / "일괄 오버라이드" |
| 사이드 패널 (lg+) | 오답 클러스터 TOP 3 (이 과제 한정) — 패턴별 학생 수 |

큐는 **지우지 않는다.** 교사가 「오늘 채점할 것」만 보고 싶은 때가 있고, 상태·타입 거르개와
AI 신뢰도 정렬은 그때만 쓰인다. 기본 화면이 학생 전체로 바뀌었을 뿐이다.

#### 3.3.2 채점 상세 (`/teacher/grading/[id]`)
| 구성 | 설명 |
|---|---|
| 헤더 | 학생명·과제명·제출 시각·"이전/다음 학생" 네비 |
| 좌측 — 문제 + 학생 응답 | KaTeX 렌더 · 학생 원본 텍스트 · OCR (있을 시) |
| 중앙 — 루브릭 카드 | 항목별 (criterion · weight · score · reason) · 인라인 슬라이더로 점수 수정 |
| 우측 — AI 초안 코멘트 + Tier 표시 | 교사 편집 가능 textarea · 변경 시 변경률 실시간 표시 |
| **변경률 패널** | 점수·코멘트 변경 % · 20% 초과 시 "루브릭 재학습 제안" 활성 |
| 액션 바 | `[승인]` · `[수정 후 승인]` · `[전체 재채점 요청]` · `[1:1 면담 메모]` |
| 사이드 — 이 학생 최근 5회 | 과거 채점 이력 추세 (점수·코멘트 유형) |
| 위기 게이트 | 응답에 자살·우울 키워드 발견 시 자동 경고 모달 (3자 알림 트리거) |

#### 3.3.3 학생 상세 (`/teacher/students/[id]`) — 채점 허브가 보내는 곳

**화면을 새로 만들지 않는다.** 이미 있는 화면이고 대화 기록 뷰어·과정 평가·이탈 이력이 들어 있다.
채점 허브에서 학생을 눌러 들어왔을 때 답해야 하는 질문은 셋인데, 앞의 둘은 **이미 답하고 있고**
셋째만 비어 있다. **이 화면에 더하는 신규 UI 는 패널 두 개다** — 「막힌 지점」(셋째 질문의 답)과
「이 학생의 채점」(채점 허브로 돌아가는 왕복 링크). 그 밖에는 아무것도 더하지 않는다.

| 질문 | 어디가 답하나 |
|---|---|
| **어떤 봇과** 대화했나 | 헤더 (`학급 · 봇 이름 · 단원`) + 대화 기록 뷰어의 말하는 이 이름 — **이미 있다** |
| **어떤 대화**를 했나 | 대화 기록 뷰어 — 턴 단위 · 범위 이탈 표시 · 지름길 표시 — **이미 있다** |
| **어디서 막혔나** | **「막힌 지점」 패널 (신규 ①)** — 막힌 개념마다 학생이 한 질문과 봇이 되짚은 말을 붙여 보여준다 |

「막힌 지점」 패널:
- 원천은 `MonitoredStudent.stuckConcepts` 하나뿐. 학급 「다시 가르칠 개념」과 **같은 값**을 읽는다
- 개념 이름 옆에 그 개념을 다룬 대화 턴(학생 질문 · 봇 되묻기)을 그대로 붙인다.
  **여기서 「대화」는 실제 대화 로그가 아니라 mock 이다** — `buildTranscript()` 가 `stuckConcepts` 등으로
  합성한 것이고(`lib/mock/classbot-student-report.ts`), 이 패널은 그 mock 에서 **뽑아 쓸 뿐 따로 만들지 않는다**.
  실제 로그는 BE 가 대화 기록을 내려주기 시작할 때 이 자리에 그대로 갈아 끼운다
- 막힌 개념이 없으면 그렇게 적는다. 빈 자리를 다른 지표로 메우지 않는다
**들어온 곳에 따라 되돌아가는 곳이 달라진다.** 이 화면은 지금 뒤로 가기·학생 이동을
관제소 기준으로 고정해 두고 있다(`backHref="/teacher/monitor"`, `backLabel="학급 관제소"`).
채점 허브에서 들어오면 그대로 관제소로 튄다 — 왕복이 성립하지 않는다.

| 항목 | 규칙 |
|---|---|
| 진입 source | `?from=` 로 넘긴다. 정의된 값은 **넷** — `grading` · `grading-queue` · `home` · `monitor`. 모르는 값·빈 값은 관제소로 본다 |
| 뒤로 가기 | `grading` → `/teacher/grading`(학생 전체) / **`grading-queue` → `/teacher/grading?view=queue`** / `home` → `/teacher` / 그 밖 → `/teacher/monitor` |
| 왜 큐를 따로 두나 | 채점 상세에서 「대화 기록」으로 건너간 교사는 **검수하던 큐로** 돌아가야 한다. `grading` 하나로 뭉뚱그리면 가장 빈번한 흐름(Flow G1)이 학생 전체 탭으로 샌다 |
| 지금 있는 진입원 | 관제소 명단(`monitor`) · 교사 홈 「먼저 볼 학생」(`home`) · 채점 허브 학생 목록(`grading`) · 채점 상세의 「대화 기록」(`grading-queue`) — 넷은 자기 `from` 을 붙인다 |
| 아직 안 붙인 진입원 | 리포트 명단(`report-roster.tsx`)도 소스상 `/teacher/students/[id]` 로 링크한다. 다만 그 화면은 **v1 후보이고 현행 계약이 아니다**([03] 메모 2 · [13] § 3.1 [S6]) — 여기서 진입원으로 계약에 넣지 않는다. `from` 을 안 붙이므로 관제소로 되돌아가고, 그것이 지금의 동작이다. 그 화면이 계약이 될 때 `?from=reports` 와 함께 이 표에 한 줄 더한다 |
| 이전·다음 학생 | 기준 명단은 **바뀌지 않는다** — 두 화면이 같은 `monitoredRoster` 를 이름순으로 본다. 다만 이동 링크는 `from` 을 **그대로 이어받아** 몇 명을 넘겨도 되돌아갈 곳이 유지되게 한다 |
| `period` | 지금처럼 그대로 이어받는다 |

「이 학생의 채점」 패널 (신규 ②):
- 이 학생 앞으로 온 채점 항목을 상태 배지와 함께 늘어놓고 `/teacher/grading/[id]` 로 보낸다
  (채점 허브 ↔ 학생 상세 왕복)
- 건수는 교사 확정을 얹은 뒤 센다 — 채점 허브 목록의 「대기」 배지와 **같은 값**이어야 한다
- 채점 항목이 없는 학생에게는 그렇게 적는다

## 4. UX Flow

### 4.1 Flow G1 — 교사 일상 채점 (가장 빈번)
```
1. 교사 홈 → "서술형 채점 대기 12건" 카드 클릭
2. `/teacher/grading?view=queue` 진입 (그 카드는 큐로 곧장 연다) → 큐 정렬: AI 신뢰도 낮은 순
3. 첫 번째 학생 행 클릭 → 상세 진입
4. 루브릭 점수 1개 수정 (-2) + 코멘트 한 줄 추가
5. [수정 후 승인] → 다음 학생 자동 이동
6. 일관 패턴: 5명 채점 = 약 7분 (수동 30분 → 80% 단축)
```

### 4.1-b Flow G0 — 오늘 제출하지 않은 학생 찾기 (기본 화면)
```
1. 교사 홈 → 「채점 허브」 진입 → 기본은 「학생 전체」 탭
2. 20명이 배지 세 벌(도달 · 최근 접속 · 채점 대기)로 한 줄씩 보인다
3. 채점 대기 0건인데 도달 배지가 「미도달」인 학생이 눈에 걸린다
4. 그 학생을 누름 → /teacher/students/[id]
5. 대화 기록에서 어떤 봇과 무슨 말을 주고받았는지, 「막힌 지점」에서 어디서 걸렸는지 확인
6. 채점 큐만 보던 때에는 이 학생이 화면에 아예 없었다 — 그게 이 화면을 바꾼 이유다
```

### 4.2 Flow G2 — 루브릭 재학습 환류
```
1. 교사가 같은 항목("표기 정확성")을 5명 연속 -5점 추가 차감
2. 시스템: 변경률 누적 24% — 임계 초과
3. 상세 페이지 우측에 "루브릭 재학습 제안" 카드 점등
4. 교사 클릭 → 변경 패턴 요약 모달
5. [다음 과제부터 적용] → 루브릭 v2 활성, 이력 감사 로그 기록
```

### 4.3 Flow G3 — 위기 신호 발견 (응답 빈약)
```
1. 학생 최도현 응답 = "잘 모르겠음. 그래프가 너무 어렵다"
2. AI 초안: 8/20 · aiConfidence 58 · 코멘트에 "응답 부족"
3. 큐에서 위기 인디케이터 점등
4. 교사 진입 → "1:1 면담 메모" 클릭
5. 메모 작성 → 리포트 센터의 학생 개인 리포트에 자동 첨부
6. 최도현이 다음 로그인 시 "선생님이 도현이를 응원해" 알림 (점수 노출 전)
```

## 5. 운영 로직 (Business Rules)

### 5.1 변경률 계산식
```
overrideDelta = |draftScore - finalScore| / maxScore × 100
```
- 누적 변경률 = 최근 30일 평균
- 30일 평균이 임계(20%) 초과 시 자동으로 루브릭 재학습 제안

### 5.2 상태 전이
```
queue ──교사 진입──> reviewing ──저장──> approved
                                  └──수정──> overridden  (overrideDelta 저장)
```
- `approved`와 `overridden` 모두 학부모·학생에게 가시화되는 종착 상태
- 재학습 후 같은 항목에 대해 점수가 자동 재계산되더라도 종착 상태는 보존

### 5.3 자동 처리 규칙
- `type === 'short' && aiConfidence ≥ 95` → T1 자동 채점 + 자동 승인 (교사 검수 스킵)
- `type === 'essay'` → 무조건 교사 검수 필수
- `type === 'numeric'` → 정답 일치 시 자동 승인, 부분 점수 케이스만 큐 진입

### 5.4 위기 게이트 (자동 차단)
응답 본문에 다음 정규식 매치 시 점수 표시 전에 경고 모달:
- 자살·자해 관련 키워드 (사전 정의 화이트리스트 기반)
- 감정 체크인 직전 3일 "힘듦" 누적 학생 응답

게이트 통과 후에만 점수 화면 노출. 동시에 [13. 리포트 + 감정 체크인](13-reports-and-emotion-checkin.md § 6.2) 의 3자 알림 트리거.

### 5.5 검증 규칙
| 항목 | 제약 |
|---|---|
| `rubric` 합 | 항상 100 (검증 실패 시 저장 차단) |
| 항목별 점수 | 0 ≤ score ≤ weight × 1.0 |
| 코멘트 길이 | 10 ≤ length ≤ 500자 |
| 승인 후 수정 | 금지 (수정 필요 시 별도 "재채점 요청" 로그) |

### 7.1 채점 시드를 학생 명단으로 정렬 (fixture alignment)

> **이 절은 계약이다. 아래 상태는 뒤따르는 코드 PR 이 만든다** — 이 리포는 문서 PR 을 먼저 머지하고
> 코드 PR 을 올린다. 지금 `dev` 의 시드는 아직 정렬 전이고, 그 어긋남이 이 절을 쓰게 만든 이유다.

**학생 모집단이 둘로 갈려 있다.**

| | 파일 | id | 학생 | 수업 |
|---|---|---|---|---|
| 채점 시드가 쓰던 명단 | `classbot.ts` · `classRoster` | `s1`~`s18` | 서연 · 민준 · 지우 · 도현 · 하윤 · 주원 | 중2 수학 A반 |
| 학생 목록·상세가 쓰는 명단 | `classbot-monitoring.ts` · `monitoredRoster` | `m01`~`m20` | 김서연 · 이준서 · 박하람 · 최도현 · 정예린 · 강주원 | 중1-3반 과학 |

`gradingQueue` 는 `studentId: 's1'` 을 쓰고 `findStudent()` 는 `monitoredRoster` 에서 `m01` 을 찾았다.
**이름이 비슷해 보이지만 다른 반·다른 과목의 다른 학생이다.** 서연(중2 수학)은 김서연(중1 과학)이 아니다.
그 상태로 채점 허브에서 학생을 누르면 **수학 제출물을 보러 왔는데 과학 대화 기록이 열렸다.**

#### 브리지 표를 만들지 않는다

`sN → mNN` 매핑을 적으면 「이 둘이 같은 사람」이라는 **없는 사실을 문서에 박는 것**이다.
번호로 이어도, 이름으로 이어도 마찬가지다 — 두 사람이 실제로 같은 사람일 때만 옳은 방법이라
여기서는 어느 쪽도 쓸 수 없다.

#### 대신 모집단을 하나로 맞춘다

**채점 쪽 시드만 `monitoredRoster` 로 옮긴다.**

- `gradingQueue` · `gradingHistory` · `overriddenSample` 의 학생을 `m01`~`m20` 으로 바꾼다
- 과목·학년·단원도 그 학생들의 것으로 맞춘다 — 중1 과학 학생이면 제출물도 **중1 과학 · 물질의 상태 변화**
- **`classRoster`(`sN`)는 지우지 않는다.** 학생 채팅·과제 발사·리마인드 등 다른 화면이 쓴다. 채점 쪽만 옮긴다

정렬 뒤에는 `GradingItem.studentId` 가 곧 학생 명단의 id 가 된다. 이름도 한 벌이고,
채점 항목에서 학생 상세로 건너가도 **같은 학생·같은 수업**이다.
잇는 표도, 어느 줄에도 붙지 못하는 항목도 없다. 권위 문서 Flow C 의 한 사이클이 mock 에서도 닫힌다.

#### 어느 학생이 어느 제출물을 갖는가

점수를 지어내지 않으려고 **그 학생의 관제 상태와 어긋나지 않는 제출물**을 붙인다.

| 채점 항목 | 학생 | 관제 상태 | 왜 이 학생인가 |
|---|---|---|---|
| `gr_001` 17/20 · 대기 | `m13` 신윤서 | 도달 3/3 · 막힌 개념 없음 | 개념은 맞고 용어만 한 번 흔들린 답 |

**점수·신뢰도·상태·루브릭 배점은 손대지 않는다.** 바뀌는 것은 학생 신원과 과목 내용뿐이라
§ 5.1 변경률·§ 5.5 검증 규칙·기존 회귀가 그대로 성립한다.

#### 지켜지는지 어떻게 아나 (코드 PR 이 함께 넣을 회귀)

`lib/mock/__tests__/classbot-grading-roster.test.ts` 가 본다.

- 모든 채점 항목이 학생 명단의 학생을 가리킨다
- 이름도 명단 이름 그대로다
- 과목·단원도 그 학생들의 수업이다 (`topic` 에 `monitoredClass.unit` 이 들어 있다)
- 채점 이력도 같은 학생을 가리킨다
- 학생별 대기 합계 = 큐 전체 대기 — 어느 항목도 새지 않는다

시드를 새로 넣을 때 명단 밖 학생을 쓰면 여기서 깨져야 한다.

#### 남는 것 — BE 연동

BE 가 `enrollments`/`studentId` 로 한 명단을 내려주면 `monitoredRoster` 도 임시 FE 시드 자리를 넘긴다.
화면은 명단을 인자로 받으므로(`buildGradingRoster(items, roster)`) 원천만 갈아 끼우면 된다.

## 8. 브랜딩 / UX Writing

### 8.1 톤
교사를 "판결자"가 아닌 "마지막 검수자"로 호칭. AI 초안은 항상 "초안" 또는 "제안"으로 표기 — 결코 "AI 채점 결과"라고 단독 표현 금지.

### 8.2 마이크로카피 테이블

| 상황 | 카피 |
|---|---|
| 큐 빈 상태 | "검수할 채점이 없어요. 학생들이 새로 제출하면 여기에 쌓여요." |
| 학생 목록 기본 설명 | "등록된 학생 전체예요. 채점할 게 없는 학생도 함께 보여요." |
| 채점 대기 0건 배지 | "대기 없음" |
| 학생 목록 거르개 빈 상태 | "이 조건에 해당하는 학생이 없어요." |
| 막힌 지점 없음 | "이 학생이 막힌 개념은 기록에 없어요." |
| AI 신뢰도 낮음 | "AI 신뢰도가 낮아요. 직접 보고 정하는 게 안전해요." |
| 변경률 20% 초과 | "루브릭이 학생 답과 어긋나는 것 같아요. 기준을 다시 학습할까요?" |
| 위기 게이트 발동 | "최도현 학생 응답에 신경 쓸 표현이 있어요. 점수 전에 한 번 더 봐주세요." |
| 일괄 승인 확인 | "선택한 N건을 그대로 승인할게요. 되돌릴 수 없어요." |
| 재학습 제안 수락 | "다음 과제부터 새 기준이 적용돼요. 이전 점수는 그대로 남아요." |

### 8.3 금지어
- "AI가 채점했어요" → "AI 초안이에요"로 교체
- "정답" → 서술형은 "기준 응답" 또는 "모범 응답"
- "오답" → "보완 필요" (학생 가시 영역)
