## 1. AI 명령지침

- **본 spec은 E2E 사이클의 진입점이다.** 봇 빌드 → **과제 내기** → 학생 수령 → 풀이 → 제출 → 채점 → 리포트의 첫 단계. 11/12/13이 사이클의 후반부를 채웠다면, 14는 시작점.
- **추출본 정책**: 백엔드 없이 **mock 데이터로 E2E가 시연되어야 한다**. 교사가 낸 새 과제가 **새로고침 후에도** 학생 화면에 보여야 — `localStorage` 기반 Zustand store로 구현.
- 추출본 정책: 다른 도메인(플래너·Q·라이브러리) 의존 금지.
- 봇 빌더 산출물 소비는 **아직 단원 하나뿐이다** — 봇을 고르면 `getBotCurriculum(botId)[0]` 이 단원으로 들어온다(`handleBotChange`). RAG 범위를 읽어 정하는 경로는 없다. 모드는 `practice` 고정 기본값이고, 톤·답 범위는 **소비하지 않는다.** 저장 payload 가 옮기는 것은 `subject` · `grade` · `chapter*` 다.
- **채점 기준은 봇에서 오지 않는다** — 문항 배점에서 파생해 과제 출제에서 만든다 (`03 § 4.3` 대응표 ⑥).
- **금지**: 학생에게 내기 전 새 과제 노출. 내기 액션(state: `draft → sent`)을 거쳐야 학생 화면 등장.
- **금지**: 과제 정보를 백엔드 가정으로 작성. P0는 클라이언트 store만, v1에서 서버 연결.

## 2. 제품 정의

### 2.1 Problem Statement
P0 완료 후 채점-풀이-리포트 사이클은 닫혔지만, **교사가 새 과제를 만드는 진입점이 없다**. `/teacher/classbot` 페이지의 `[+ 새 과제]` 버튼은 빈 핸들러이고, 학생이 받는 과제는 **mock 시드 3건에만 의존**한다. 결과적으로 데모/시연이 "교사가 낸 것 같은 가짜 데이터"에 머문다.

### 2.2 Product Goal
- **G1**: 교사가 **5분 안에** 1개 과제를 낼 수 있다 (단일 페이지 네 섹션 폼)
- **G2**: 낸 과제가 **즉시** 학생 홈 PrimaryCard·받은 과제 목록에 자동 반영
- **G3**: E2E 시연 — 봇 빌드부터 학부모 리포트까지 **mock으로 끝에서 끝까지 돌아간다**
- **G4**: 봇을 고르면 단원이 따라와 입력 부담을 줄인다. (모드·톤·답 범위까지 흡수하는 것은 **후속 과제** — 지금은 소비하지 않는다)

### 2.3 Persona

| 페르소나 | 이 기능에서 무엇이 달라지나 |
|---|---|
| **P1 교사** (주) | 매 수업 후 5분이면 과제 하나를 내는 것이 일상화 — "오늘 어려웠던 단원 5문항" 즉시 처방 |
| **P2 학생** | 받는 과제가 mock이 아니라 "방금 선생님이 보낸 것"으로 인식됨 (홈 알림 + 뱃지) |
| **P3 학부모** | 자녀가 실제 받은 과제 진행률이 주간 리포트에 반영 |

## 3. 핵심 기능 정의

### 3.1 MoSCoW

#### Must (이번 P0)
- [M1] 단일 페이지 네 섹션 폼 — 정체성·문항·대상·일정
- [M2] 봇 선택 시 그 봇의 커리큘럼 첫 단원 자동 선택. 채점 기준은 봇이 아니라 **문항 배점에서 파생**한다
- [M3] 모드별 분기 UI:
  - `practice`: 봇 힌트 단계 설정
  - `exam`: 시험 모드 토글 + 시간 제한 + Scope L1 자동 override 안내
  - `wrong-conquest`: 봇이 감지한 학생 오답 패턴 자동 제안 (시드)
- [M4] **클라이언트 store** (Zustand + localStorage) — 낸 과제가 새로고침 후에도 학생 화면에 보존
- [M5] 학생 측 자동 반영 — `/classbot` 홈·`/classbot/assignment` 목록·BottomNav 뱃지
- [M6] 낸 직후 토스트 + 학생 화면 미리보기 모달 (교사가 "어떻게 보이는지" 즉시 확인)

#### Should (v1)
- [S1] 예약해서 내기 — 정한 시각에 자동으로 나간다 (수업 시작 시간 등)
- [S2] 봇 처방 자동 생성 — 학생 오답 패턴 N개 누적 시 봇이 자동 draft 생성
- [S3] 여러 반에 한 번에 — 같은 과제를 여러 반에 동시에 낸다
- [S4] 과제 템플릿 — 자주 쓰는 형식 저장·복제
- [S5] 통합 과제 목록 — `/teacher/assignment` (다중 봇 운영 시 모든 과제 한눈에)

#### Could (v2)
- [C1] AI 자동 문항 추천 — RAG 인덱스에서 학생 수준 맞춤 문항 자동 선정
- [C2] 루브릭 사전 편집 — 내기 전 항목별 가중치 조정 (현재는 문항 배점에서 파생한 기본값)
- [C4] 봇 산출물 흡수 확대 — 봇의 수업 방식 → 과제 기본 모드, 답 범위·톤 → 기본값. 지금은 단원만 따라온다
- [C3] 구글 클래스룸 동기 — 과제 양방향 동기

#### Won't (현 단계 제외)
- 낸 뒤 수정 — 학생이 받은 후 수정 시 혼란. 회수·다시 내기 패턴으로만.
- 학생이 직접 만든 과제 (`source: 'self'`) — v3+ 자율 학습 영역

### 3.3 Screen Spec

#### 3.3.1 과제 내기 워크스페이스 (`/teacher/assignment/new`)

단일 페이지 + sticky bottom 액션 바. 모바일 대응은 v1 (교사 데스크탑 우선).

> **⚠ 이 절의 `[예정]` 은 아직 `dev` 에 없다.** 표기 관례는 `00-index § 48` 을 따른다 —
> 표기 없는 줄은 **현재 동작 설명**이고, `[예정]` 이 붙은 줄은 **후속 FE PR 이 통과해야 할
> 기준**이지 지금 화면이 아니다. 2026-09-14 결정(용어·배치·진행도)은 **이 문서가 먼저**이고
> 코드는 뒤따른다 — 순서를 그렇게 잡은 이유는 § 8.1 머리에 적었다.
>
> `dev` 의 `assignment-form.tsx` 는 지금 **`발사 봇` · `과제 발사하기` · `진행도 {progress}/5` ·
> `발사 →`** 를 그대로 렌더한다. 같은 PR 이 고친 `2026-07-03_…-ddl.md` § 3 이
> `assigned_at_label='방금 발사'` 를 **코드 실값**으로 적어 둔 것과 같은 사실이다.

| 섹션 | 구성 | 자동 채움 |
|---|---|---|
| **① 정체성** `[예정]` | 수업방 선택(드롭다운) — 현재 라벨은 `발사 봇` · 제목 · 모드(practice/exam/wrong-conquest) · 난이도(하/중/상) · 봇 한 마디 (선택, 200자 — **현재는 ④ 에 있다**) | 수업방 선택 시 학년·과목 자동 |
| **② 문항** | 단원 from-to · 문항 수 · 자동 생성 / 수동 선택 토글 · (수동 시) 문항 추가 모달 | 선택한 수업방 봇의 curriculum 첫 단원 자동 선택 |
| **③ 대상** `[예정]` | 기본은 **반 전체**로 접어 둔다 — **현재는 명단 그리드가 항상 펼쳐져 있다.** — `대상 · 반 전체 N명 [바꾸기]` 한 줄. 펼치면 학생 명단(체크박스) · "전체 선택" · 선택 N명 표시 | 수업방 선택 시 enrolled 학생 자동 체크 |
| **④ 일정** | 마감일 (D-day picker) · 바로 내기 / 예약해서 내기 (v1) · ~~봇 한 마디~~ → ① `[예정]` | "내일 22:00" 기본 채움 |

> **① 이 네 섹션뿐이다 — ⑤ 는 두지 않는다.** 종전 표는 `⑤ 발사`(미리보기 · 최종 검토 체크리스트 · 버튼)를
> 섹션으로 세었고 아래 액션 바가 그것을 「5섹션 중 N완료」로 셌다. 구현은 ⑤ 를 섹션으로 만들지 않고
> sticky 액션 바로 흩었는데, 그 결과 **화면 번호는 ④ 에서 끊기는데 진행도만 5 를 분모로 쓰는** 상태가
> 남았다(빈 폼이 이미 「4/5」로 뜬다 — 제목 말고는 전부 기본값이 채워지기 때문이다).
> **진행도 표시를 없애는 것으로 정리한다**(2026-09-14 결정 · `[예정]`, 아래 § 3.3.1 액션 바).
> 막힌 이유는 숫자가 아니라 **문장**으로 말한다 — 액션 바의 차단 사유 한 줄이 그 자리다.

> **「봇 한 마디」가 ④ 에서 ① 로 옮겨 온다**(2026-09-14 결정 · `[예정]`). 이 값이 저장되는 컬럼은 `reason_hint` 이고
> 학생 화면에 `reasonHint` 로 내려가 **「왜 이 과제를 받았는지」**를 말한다(`12 § 3.3.2`). 일정이 아니라
> 이 과제가 무엇이고 왜 있는지에 속한다. **데이터는 바뀌지 않는다** — 어느 섹션에서 그리는지만 바뀐다.

**시험 모드 추가 섹션** (`mode === 'exam'`일 때만 노출):
- 시간 제한 (분)
- 외부 탭 카운트 정책 (3회 초과 시 자동 제출 / 카운트만)
- Scope override = L1 안내 ("낸 뒤엔 봇이 잠겨요")
- 이전 문항 이동 허용 토글

**상단 컨텍스트 바**:
- 좌: `[← 취소]` (변경 사항 있으면 확인 모달)
- 중: "새 과제 — {봇 이름}"
- 우: 임시 저장 인디케이터 ("방금 전 저장됨")

**Sticky bottom 액션 바**:
- 좌: `[미리보기]` (학생 시점 모달) · `[임시 저장]` (draft 유지)
- 중: **막힌 이유 한 줄** (이미 있다 — `blockedReason`) — 못 내는 상태일 때만 노출한다(예: "배점 합계 90/100점 — 맞춰야 낼 수 있어요")
- 우: `[과제 내기]` (모든 필수 통과 시 활성) — `[예정]` · 현재는 `발사 →`
- **진행도 숫자는 두지 않는다**(2026-09-14 결정 · `[예정]` — 현재는 `진행도 {progress}/5` 를 렌더한다). 종전 「5섹션 중 N완료」는 위 § 3.3.1 주석 참고.
- **폭은 본문과 같아야 한다** `[예정]` — 액션 바와 상단 컨텍스트 바 둘 다 `max-w-3xl` 안쪽에 정렬한다(§ 9.3).

#### 3.3.2 학생 시점 미리보기 모달
- 학생 홈 `PrimaryAssignmentCard`와 동일 디자인
- 모드별 색상·뱃지 그대로
- 시험 모드일 경우 경고 카드도 미리보기

## 4. UX Flow

### 4.1 Flow A1 — 수업 후 바로 내기 (가장 빈번)
```
1. 19:50 수업 종료 → 교사 /teacher/classbot
2. "낸 과제" 섹션 [+ 새 과제] 클릭
3. /teacher/assignment/new 진입 → "수학이 형" 수업방 자동 선택
4. ① 정체성: 제목 "도함수 활용 복습", 모드 practice, 난이도 중
5. ② 문항: 단원 "극값~변곡점", 자동 생성 N=10
6. ③ 대상: 18명 전체 (자동 체크됨)
7. ④ 일정: 내일 22:00 (자동 채움)
8. 미리보기 → 카드 확인 → [과제 내기]
9. 토스트 "18명에게 냈어요" + 자동 /teacher/classbot 복귀
10. "낸 과제" 섹션에 새 행 등장
```

### 4.2 Flow A2 — 봇 처방 자동 생성 시연 (v1, P0는 mock 트리거)
```
1. 학생 도현 오답 누적 3건 (mock 시드)
2. 시스템 자동 — `source: 'bot-prescribed'` draft 생성
3. 교사 홈 알림 "수학이 형이 도현이를 위해 새 과제를 준비했어요"
4. 교사 검토 → 한 줄 추가 또는 그대로 [과제 내기]
5. 학생 도현 홈에만 노출 (대상 = 1명)
```

### 4.3 Flow A3 — 시험 모드 내기 (Scope L1 강제)
```
1. /teacher/assignment/new → 모드 'exam' 선택
2. 시험 모드 섹션 자동 펼침 — 60분 / 외부 탭 3회 / Scope L1 안내
3. ② 문항: 30문항 수동 선택 (자동 생성 + 직접 추가)
4. ④ 일정: 5/18 19:00 (예약해서 내기)
5. [과제 내기] → 5/18 19:00에 자동 등장 안내 토스트
6. 학생: 5/18 19:00 도달 시 홈에 시험 카드 등장 (mock — P0는 바로 내기만, 예약은 v1)
```

### 4.4 Flow A4 — 다중 봇 운영 (v1)
```
1. 김수학 선생님 → 봇 3개 운영 ("수학이 형", "영어 누나", "과학 쌤")
2. /teacher/assignment 통합 목록에서 봇별 내기 이력 확인
3. 같은 과제를 영어 누나·수학이 형에서 동시에 낸다 (S3 여러 반에 한 번에)
```

## 5. 운영 로직 (Business Rules)

### 5.1 내기 전 검증

> 있고 교사가 거기서 고르는 흐름을 전제했는데, **참여 코드**가 생기면서 「반을 먼저 열고

> 학생이 들어올 때까지 아무것도 낼 수 없다. 빈 방에 내면 **빈 배열 = 반 전체**로 저장되고,
> 뒤에 참여한 학생이 그 과제를 받는다. 필드 이름은 층마다 다르다 — 이 문서의 ERD·FE 는

> 이 절이 정하는 것은 **「빈 배열의 뜻」**이지 필드 이름이 아니다.
>
> 대신 **명단을 못 읽은 상태**(조회 실패·응답 전)는 내는 것을 막는다. 그 상태의 빈 배열은
> 「학생이 0명인 반」과 모양이 같아, 막지 않으면 교사가 명단을 한 번도 보지 못한 채 전원에게

### 8.1 톤

> **2026-09-14 개정 — 「발사」를 버리고 「내기/내다」로 통일한다.**
> 종전 이 항은 *"'발사'라는 단어 톤 유지 — 현재 코드 `DispatchedAssignments` 에서 사용 중"* 이었다.
> 그것이 **근거를 거꾸로 세운 조항**이었다 — 코드에서 난 말을 스펙이 사후 승인한 것이고,
> **권위 문서(`input/docs-archive/**`)에 「발사」는 0회다.** 거기서 쓰는 말은 「과제 출제」(`07:132` · `07:166` ·
> `05:291`)와 「과제 생성」(`07:310`)이다. 그리고 이 리포의 화면들이 이미 답을 정해 두고 있었다 —
> 이 워크스페이스로 들어오는 **입구 넷 중 셋이 이미 「과제 내기」**이고, 학생 화면도
> "선생님이 새 과제를 **내면**"이라고 말한다. **「과제 내기」를 눌렀는데 「과제 발사하기」에
> 도착하는** 상태였다.
>
> | 입구 | 현재 라벨 | 정본 |
> |---|---|---|
> | `teacher/page.tsx:60` 빠른 액션 | 과제 내기 | 그대로 |
> | `teacher/classbot/page.tsx:176` 봇 카드 더보기 | 과제 내기 | 그대로 |
> | `teacher/classbot/page.tsx:399` 빈 상태 CTA | 과제 내기 | 그대로 |
> | `teacher/classbot/page.tsx:394` 목록 헤더 CTA (`new-assignment-cta`) | **새 과제** | **과제 내기** `[예정]` |
>
> **네 번째가 혼자 다르다.** 같은 `/teacher/assignment/new` 로 가는데 라벨만 「새 과제」다 —
> 통일 범위에 넣지 않으면 도착 화면을 고쳐도 **입구 하나가 다른 이름으로 남는다.**

- **동사는 「내다」** — 과제를 낸다. 화면 제목과 주 버튼은 **「과제 내기」**로 통일한다.
- 학생 측 통보는 부드럽게 — "선생님이 새 과제를 보냈어요" (가벼운 무게)
- 시험 모드는 차분하게 — "시험 과제예요. 시작하면 멈출 수 없어요"
- **교사 화면은 한자어를 피하지 않는다** — 학생·학부모 화면에만 걸리는 규칙이다(교사는 읽기 부담이 없다).
  그래도 **비유·은어·뜻이 모호한 말**은 교사 화면에서도 고친다. 기준은 「학교에서 실제로 쓰는 말인가」다.

#### 8.1.2 「내다」는 주체에 따라 뜻이 뒤집힌다 — 주어가 없으면 박는다

우리말 **「과제를 내다」는 두 뜻**이다. 교사가 내면 **부과**고, 학생이 내면 **제출**이다.
이 리포에 둘 다 이미 있다:

| 화면 | 문구 | 「내다」의 뜻 |
|---|---|---|
| 교사 `/teacher/classbot` | "아직 **낸** 과제가 없어요" | 부과 |
| 학생 풀이 결과 | "**냈어요** · **낸** 답은 풀이 화면에 있어요" | 제출 |

**각 역할의 화면 안에서는 문제가 없다** — 주체가 화면으로 정해져 있다. 조심할 자리는 셋이다:

1. **주어 없는 명사구** — 「낸 과제」만 덩그러니 있으면 반대로 읽힌다.
   특히 `… → 제출 → …` 같은 흐름 서술 바로 앞이면 더 그렇다.
   → **주체를 박는다**: 「교사가 낸 과제」 · 「학생이 낸 답」.
2. **학부모 화면**(`app/(parent)/*`) — 자녀의 과제를 보여 주는 자리라 주체가 둘 다 등장한다.
   → 부과 쪽은 **「선생님이 낸」**, 제출 쪽은 **「제출」**로 갈라 쓴다.
3. **문서·API·로그 서술** — 화면 맥락이 없다. → 1번과 같게 주체를 박는다.

**학생 화면의 「받은 과제」 · 「제출」은 그대로 둔다.** 이 개정은 **교사가 과제를 부과하는 쪽**의
용어만 바꾼다 — 학생 쪽 어휘까지 끌고 가면 바로 이 충돌을 화면에서 만든다.

| 자동 채움 안내 | "{봇 이름}이 가르치는 단원으로 맞췄어요." |
| 문항 자동 생성 | "{단원}에서 {N}문항을 추천했어요. 마음에 안 들면 다시 뽑을 수 있어요." |
| 대상 학생 전체 선택 | "{N}명 전체에게 보낼게요." |
| 시험 모드 토글 시 | "시험 모드 — 봇이 자동으로 잠기고 시간 제한이 걸려요." |
| 못 내는 이유 (액션 바) | "{막힌 이유} — 맞춰야 낼 수 있어요." (진행도 숫자를 대신한다) |
| 미리보기 모달 헤더 | "학생들에게 이렇게 보여요" |
| 내기 직전 확인 | "{N}명에게 지금 보낼게요. 낸 뒤엔 수정할 수 없어요." |
| 내기 성공 토스트 | "{봇 이름}이 {N}명에게 보냈어요." |
| 임시 저장 | "임시 저장했어요. 언제든 이어서 만들 수 있어요." |
| 검증 실패 | "{필드}를 마저 채워주세요." |
| 학생 홈 새 과제 알림 | "선생님이 새 과제를 보냈어요. 마감 D-{N}" |

#### 8.2.1 ① 모드 고르기 — 라벨과 설명 (2026-09-14 확정 · `[예정]`)

**라벨은 「봇이 답해 주는 범위」다.** 종전 「봇 개입 강도 (모드)」를 쓰지 않는다 — **현재 코드는 아직 그 라벨이다.** — 이 스펙에서
**「개입」은 교사 개입**(리마인드·코멘트·다시 내기·응원, `2026-07-02_classbot-teacher-intervention-design.md`)을
가리키는 말이고, 봇이 어디까지 답하는지를 가리키는 말은 **Scope / 답 범위**(`05 § 2`)다. 용어가 충돌했다.

| 모드 | 설명 (한 문장) | 근거 Scope |
|---|---|---|
| 연습 | "힌트는 주고 정답은 안 알려 줘요" | L4 — 단계별 힌트, **정답 직답 차단** |
| 시험 | "봇이 잠기고 시간을 재요" | L1 — 봇 응답 차단, 메타데이터만 |
| 오답정복 | "정답도 해설도 바로 보여 줘요" | L5 — 정답·해설·반례 즉시, 단계 건너뛰기 가능 |

세 줄은 **같은 꼴의 한 문장**으로 쓴다(「~요」로 끝난다). 교사가 고를 때 필요한 것은
**봇이 무엇을 안 하는지**라서 연습의 「정답은 안 알려 준다」가 문장 안에 들어가야 한다.

**라벨이 제 일을 하면 밑의 해명 문단은 지운다.** 종전 "모드는 푸는 동안 봇이 어디까지
도와줄지를 정해요 / 점수를 누가 매기는지는 ② 문항의 유형이 정해요" 두 줄은 **라벨이 틀려서
필요해진 설명**이었다.

#### 8.2.2 ② 문항 — 채점 방식 배지 (2026-09-14 확정 · `[예정]`)

배지는 **`자동 채점` · `선생님이 채점` 두 라벨만** 둔다. **밑에 붙던 설명 한 줄은 두 쪽 다 지운다.**

- `봇이 답을 바로 맞혀 봐요`(자동) — **버린다.** 뜻은 "봇이 즉시 채점한다"인데 *"봇이 답을
  알아맞힌다"*로도 읽히고, 하필 옆 축(오답정복)에 **진짜로 정답을 즉시 공개하는 동작**이 있어
  오독이 실재하는 다른 기능에 가서 붙는다.
- `낸 뒤에 선생님이 직접 봐요`(교사) — **짝이라 함께 버린다.** 한쪽만 지우면 배지가 안 맞는다.
- 두 줄 다 **② 섹션 안내문과 중복**이다 — "객관식 · 단답 · 수치는 봇이 자동으로 채점하고,
  서술형은 선생님이 채점 허브에서 직접 봐요"가 이미 같은 말을 한다.
- 더구나 배지 설명은 **문항마다 반복**된다. 5문항이면 같은 줄을 다섯 번 읽는다.

#### 8.2.3 ② 문항 — 배점 버튼 `[예정]`

`고르게 나누기` → **`점수 자동 분배`**. 무엇을 나누는지가 라벨에 없었다.
교사 화면이라 한자어를 피할 이유가 없다(§ 8.1 마지막 항).

### 8.3 금지어

> **2026-09-14 개정 — 앞의 두 줄이 뒤집혔다.** 종전에는 `"출제" → "발사"` · `"배포" → "발사"` 로
> **「발사」를 강제**했다. § 8.1 의 근거대로 그 방향이 거꾸로였다.

- **"발사" → "내기/내다"** (비유를 버린다. 과제는 발사하는 것이 아니라 내는 것이다)
- **"재발사" → "다시 내기"**
- "배포" → "내기" 또는 "보냈어요" (B2B 톤 회피 — 이 항의 취지는 그대로 살아 있다)
- "강제 종료" (시험 외부 탭 자동 제출) → "자동 제출" (중립)
- **"출제"는 금지어가 아니다** — 명사 자리에서는 쓸 수 있다(권위 문서가 쓰는 말이다).
  다만 이 화면의 제목과 주 버튼은 입구와 맞춰 **「과제 내기」**로 고정한다.

### 9.3 레이아웃
- 데스크탑 우선 — `/teacher/*` 와이드 규칙
- 메인 영역 `max-w-3xl` 가로 정렬 (네 섹션 폼 가독성)
- sticky bottom 액션 바 — 화면 하단 고정, 미리보기 + 임시 저장 + 막힌 이유 + `[과제 내기]`
- **`max-w-3xl` 은 폼 카드단에만 걸리는 것이 아니다** `[예정]`. 상단 컨텍스트 바와 sticky 액션 바도 **같은 캡 안**에
  들어가야 한다. 캡이 카드 래퍼에만 걸리면 좌측 정렬선은 하나인데 **우측 정렬선이 둘로 갈린다**
  (1440px 실측: 카드단 `right 1069` vs 바·헤더행 `right 1396` — **327px 어긋남**).
  주 버튼이 카드 오른쪽 끝보다 223px 바깥에 앉아 시선 밖으로 나간다.
- **액션 바는 불투명하다** `[예정]` — 본문 마지막 줄을 덮지 않도록 하단 예비 여백을 바 높이(약 70px) 이상 둔다.
  모바일은 `pb-24` 로 이미 막혀 있고 **데스크탑이 24px 뿐이라 글자가 먹힌다.**
